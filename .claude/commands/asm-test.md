# 実CPU上での使い捨てアセンブリテスト

「この命令を実行したら実機同然のHuman68k環境でどうなるか」を、NMIベクタ乗っ取り
のようなハックではなく**本物の.X実行ファイル**として検証する手順。例外/バスエラー
時のPC・SR等、CPUの正確な実行順序に依存する挙動を確認したいときに使う
（x68000#23 のバスエラーPC/SR検証で確立した手順）。

## 前提ツール

```bash
brew install yunkya2/tap/elf2x68k   # m68k-xelf-gcc/as, elf2x68k.py
```

XDFへの書き込みは `tools-host/hu68disk/hu68disk`（本プロジェクト自作、要ビルド）を使う。
**mtools（mcopy）は使わないこと**: VFAT長名(LFN)エントリを生成し、Human68kが
「無効なメディアを使用しました」と誤認する既知の問題がある（2026-07-12発見）。
ファイル名は拡張子込み最大21バイト（Human68kネイティブ長名の上限）に収めること。

## 手順（HOSTDRV経由・通常はこちらが楽）

**通常の開発用 `ix68k.cfg`（SCSI HDD起動）で既にエミュレータが起動中**なら、
フロッピー経由の手順0〜3は不要。CONFIG.SYSに`DEVICE = \SYS\HOSTDRV.SYS`が
組み込み済みで、`hostdrv_dir`（既定`tests/work`）がHuman68kから読み取り専用
ドライブとして見える（このドライブレターはSCSI接続台数で変わる。`DIR`で
volume名`work`のドライブを探す。2026-09時点では`F:`）。

1. ビルドした`.X`を`tests/work/`（`hostdrv_dir`）へ直接コピーする
   （`m68k-xelf-gcc`/`elf2x68k.py`の出力をそのまま、`build.sh`のXDF書き込み部分は使わない）。
2. `run_command("DIR F:")`で見えることを確認し、`run_command("F:FOO")`で実行する。

hu68disk/フロッピーのinsert-ejectダンスが不要になる分速い。ただし**HOSTDRVは
読み取り専用**で、`x68000_asmtest.cfg`（FD0強制起動、SCSI/HOSTDRV非接続、
x68000#94のドライブレター固定用）では使えないため、ドライブレター依存の
挙動を検証したい場合や書き込みを伴うテストは従来どおりフロッピー手順を使う。

## 手順（フロッピー経由・ドライブレター固定が必要な場合）

0. エミュレータは **`tools-x68k/asmtest/x68000_asmtest.cfg`** で起動する:
   ```bash
   ./build/ix68k -config tools-x68k/asmtest/x68000_asmtest.cfg
   ```
   SCSI HDDを接続せずFD0起動を強制する専用configで、Human68kのドライブレターを
   `A:=FD0, B:=FD1` に固定してある（x68000#94。起動デバイスでB:がずれる問題の
   詳細は `/mcp-debug` の「ドライブレター割り当て」参照）。`ix68k.cfg`（通常の
   開発用、SCSI HDD起動）で起動するとFD1が`B:`に見えないことがあるので注意。
1. `tools-x68k/asmtest/template.s` をコピーしてテスト内容を書く（GNU as 構文、
   `%d0`/`%a0` レジスタ接頭辞、DOS コールは `.word 0xff00` のような Line-F
   即値埋め込み。詳細はテンプレート内コメント参照）。
2. ビルドしてフロッピーへ書き込む:
   ```bash
   tools-x68k/asmtest/build.sh path/to/foo.s disk/WORK.XDF
   ```
   `FOO.X` が `disk/WORK.XDF`（`x68000_asmtest.cfg` の `fd1`、Human68k から
   `B:`）にコピーされる。
3. エミュレータ起動中でも **`disk(action="eject", media="fd", index=1)` →
   `disk(action="insert", media="fd", index=1, path=...)`** でホットスワップ
   すればよい（2026-07-08、`_B_DRVCHK` mode=8 排出検査の修正でHuman68k の
   ディレクトリ/FATキャッシュも正しく無効化されるようになった。insert 単体
   （eject を挟まない）ではキャッシュは更新されないので注意——必ずペアで
   呼ぶこと）。プロセスの完全再起動は不要。
4. MCP で実行して観察する:
   ```
   run_command("DIR B:")     # ファイルが見えることを確認
   run_command("B:FOO")      # 実行（フォールト系は run_command がタイムアウト
                              # せず、白帯表示のまま制御が返ることが多い）
   screenshot()              # 白帯の文言・PC/SR を確認
   get_registers()
   ```
5. 白帯（エラーダイアログ）が出たら `paste_text("A")` で中止して `A>` に戻す。
   次のテストを走らせる前に `run_command("DIR A:")` 等で正常復帰を確認する
   （中止後の状態がおかしいまま次のテストを重ねると原因切り分けが難しくなる）。

## テストプログラムの終了方法

- **標準は正常終了**: `mouse_curgt_test.s`のように、キー入力待ち
  （`_B_KEYSNS`等）をポーリングして検知したらDOS `_EXIT`する形を既定にする。
  無限ループを書くときは必ずこの脱出経路を用意すること。
- **`send_interrupt`（NMI/BREAK相当）は最終手段**: 正常終了が効かない
  （プログラム側のバグでキー入力チェックまで到達しない等）ときに使う。
  Human68kのBREAKダイアログ（中止`<A>`/再実行`<R>`/無視`<I>`）が出るので
  `paste_text("A")`で中止すればコマンドラインに戻れる（2026-09-08、
  マウス座標検証セッションで動作確認済み）。乱用しない——正常終了できる
  プログラムに対して都度NMIで打ち切るのが常態化すると、本来検出したい
  「プログラム側のフリーズ/無限ループ」をNMI待ちの動作と誤認しやすくなる。
- 正常終了が効かずNMIも効かない（BREAKダイアログさえ出ない）場合に初めて
  エミュレータの`reset`を検討する。resetはSRAM等の状態もリセットされるため、
  NMIより一段階重い手段として最後に回すこと。

## 注意点・ハマりどころ

- **1回の起動につき最初の1本だけ再現性が高い**。同一セッションで複数の
  フォールトテストを連続実行すると、稀に無関係なタイミングでハング/クラッシュ
  することがあった（原因未特定、x68000#23 コメント参照）。疑わしい結果が出たら
  面倒でも一度プロセスを再起動してから単独で再実行し、再現するか確認すること。
- `elf2x68k.py` は `-nostartfiles` を付けても `__INIT_SECTION__`/
  `__FINI_SECTION__`（LINK/UNLK/RTSだけの数命令）を末尾に追加する。実行が
  そこに到達することは無いので無視してよい。
- ヘッダは64バイト固定（"HU"マジック）。コードは常にファイルオフセット
  `0x40` から始まる。
- **Human68kのバスエラー/アドレスエラー表示のPCは単純な「フェッチ完了直後−2」
  ではない**。実機ROM（$FF05E4共有ハンドラ）は、例外フレームのスタック済みPCから、
  同フレームのIRフィールド（SSP+6）と一致するワードを最大5ワード
  （オフセット0, −2, −4, −6, −8, −10バイト）遡って探索し、一致した位置で
  PCフィールドを上書きする「命令先頭復元」アルゴリズムを持つ（探索範囲内に
  一致がなければ補正せずそのまま）。IRフィールドが実際にフェッチ済みの
  opcodeと一致していれば、この探索はオフセット0（＝命令先頭）で即一致するため、
  表示PCは命令先頭になる。拡張ワードを持つ命令（abs.L等）でIRを正しく保持
  していない実装では、たまたま近傍の即値等とIRが一致して誤補正が起こり、
  命令先頭からずれた値が表示されることがある（mc68000#10で発見・修正）。
  検証時はXEiJ等の参照実装で同一ROM・同一命令を実行した結果と表示PCを
  突き合わせるとよい。
