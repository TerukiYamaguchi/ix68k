# リリースビルドの PGO 設計

## 1. 目的と対象範囲

- この文書が定める対象:
  - リリース ZIP に入る ix68k を、Clang の PGO（プロファイルに基づく最適化）でビルドする仕組み
  - 計装ビルドの作り方、プロファイルの採取手順、プロファイルの管理と適用、古くなったときの扱い、検証
- 対象外・非目標:
  - 開発ビルド（`RelWithDebInfo` など）への適用。通常のビルドは変えない
  - Linux（GCC）と Windows（MSVC）の PGO。コンパイラごとに仕組みが違うため、初版では扱わない
  - 利用者がソースからビルドするときのプロファイル生成。学習に ROM・ディスク・GCC.X が要り、利用者環境では再現できない
  - エミュレーションの精度を変える最適化。PGO はコンパイラの最適化だけで、出力は変わらない
- 利用者または開発者に見える制約:
  - プロファイルはメンテナが採取してコミットする成果物である
  - 初版の対象は macOS arm64（Apple clang）だけ。他のホストは従来どおりのビルドになる

## 3. 設計の要点

- **プロファイルをリポジトリにコミットし、リリースビルドが自動で適用する。** 開発ビルドは PGO を使わない。
- 計装ビルドは CMake オプション 1 つで作る。計装ビルドだけに、終了時にプロファイルを書き出す処理を入れる。通常のビルドのコードは変わらない。
- 古いプロファイルは「無効」ではなく「劣化」として扱う。コンパイラが不一致の関数を無視して、残りは最適化する。不一致の件数をビルドのたびに記録し、コアの主要関数が変わったときに再生成する。
- 採らない案:

| 案 | 採らない理由 |
| --- | --- |
| 利用者がビルド時にプロファイルを生成する（2 段ビルド） | 学習に ROM・ディスク・GCC.X が要り、配布物に入れられない |
| CI で毎回プロファイルを生成する | ROM 不要の自動学習ワークロードがない。CI はビルド確認だけ |
| LTO | 以前の測定で効果が見られなかった |
| 精度を落とす最適化（レジスタ退避の遅延化など） | PGO で BENCH の hard-overload がほぼ消えるため、当面は不要 |
| プロファイルのテキスト形式での管理 | サイズが大きく、差分を読んでも意味がない |
| リリースのたびに必ずプロファイルを再生成する | 採取に約 10 分と計装・適用の 2 回のビルドがかかる。古いプロファイルでも約 12% 減が残るため、コアの主要関数が変わらない限り再生成の利益が小さい |

## 4. 構成とデータモデル

- 用語:
  - 計装ビルド: 実行時に分岐・関数の実行回数を数えるコードを入れたビルド。実行するとプロファイル（`.profraw`）を書き出す
  - プロファイル: `.profraw` を `llvm-profdata merge` で 1 つにまとめた `.profdata`
  - 適用ビルド: プロファイルを使って最適化したビルド。リリース ZIP に入る
- 主なファイル:
  - `CMakeLists.txt`: オプションの定義、コンパイラ・リンカのフラグ
  - `src/main.c`: 計装ビルドだけの SIGTERM ハンドラ
  - `tools-host/pgo/`: 学習スクリプトと採取手順書
  - `packaging/release/pgo/<パッケージ名>.profdata`: プロファイル。例: `ix68k-macos-arm64.profdata`（約 0.4MB）
  - `packaging/release/pgo/README.md`: 採取情報（採取日、ソースのコミット、コンパイラの版、学習内容、不一致の件数）
  - `packaging/release/stage.sh`: 適用ビルドの組み込み
- 所有関係: プロファイルはメンテナが採取してコミットする。更新のタイミングは、コアの主要関数が変わったとき（6.4）。
- サブシステム間の境界: `extern/cmc68000` を含む全ターゲットに同じフラグを適用する。mc68000 のソースは変えない。

## 5. インターフェース／レジスタ／入力

### CMake オプション

| オプション | 既定 | 動作 |
| --- | --- | --- |
| `X68K_PGO_GENERATE` | OFF | ON のとき計装ビルドにする。`-fprofile-instr-generate` をコンパイルとリンクに付け、マクロ `X68K_PGO_GENERATE=1` を定義する |
| `X68K_PGO_PROFILE` | 空 | `.profdata` のパス。指定すると `-fprofile-instr-use=<パス>` を付け、`-Wno-profile-instr-unprofiled` を加える |

- どちらも `add_subdirectory(extern/cmc68000)` の前で `add_compile_options` / `add_link_options` に設定する。MSVC の `/utf-8` と同じ位置で、mc68000 にも届く。
- 次の場合は `FATAL_ERROR` にする。指定したのに PGO が効かない配布物を、気づかずに作らないため。
  - `X68K_PGO_GENERATE` と `X68K_PGO_PROFILE` の両方を指定した
  - コンパイラが Clang 系（`Clang` または `AppleClang`）ではない
  - `X68K_PGO_PROFILE` のファイルが存在しない
- `-Wprofile-instr-out-of-date`（不一致の警告）は既定のまま警告として出す。`-Wno-profile-instr-unprofiled` は、プロファイルに載らない外部ライブラリ（softfloat など）の警告だけを抑える。テスト用ターゲット（`enable_testing()` 以降）は `-UNDEBUG` などで `ix68k` と別の定義になり不一致が出るため、`-Wno-profile-instr-out-of-date` を付けて抑える。

### 環境変数

| 変数 | 用途 |
| --- | --- |
| `LLVM_PROFILE_FILE` | 計装ビルドの出力先。例: `<ディレクトリ>/p-%p.profraw` |

### `stage.sh`

- パッケージ名（例: `ix68k-macos-arm64`）に対応するプロファイル `packaging/release/pgo/<パッケージ名>.profdata` があれば、`-DX68K_PGO_PROFILE=<パス>` を渡す。無ければ従来どおり（PGO なし）。
- 先に `ix68k` ターゲットだけをビルドし、そのログから `profile-instr-out-of-date` の件数を数えて表示する（テスト用ターゲットは別の定義でコンパイルされ、全体ビルドの警告数は指標にならないため）。

### `stage.ps1`（Windows clang-cl）

- `stage.sh` と同じ方式。`ix68k` ターゲットを先にビルドして `build\release\build_ix68k.log` に残し、`profile-instr-out-of-date` の件数だけを表示する。

## 6. 動作仕様

### 6.1 プロファイルの採取手順

メンテナが、ROM・ディスク・GCC.X が揃った環境で行う。

1. 計装ビルド: `cmake -S . -B <計装用ディレクトリ> -DCMAKE_BUILD_TYPE=Release -DX68K_PGO_GENERATE=ON` → `cmake --build <計装用ディレクトリ> --target ix68k`
2. 学習: `LLVM_PROFILE_FILE=<出力ディレクトリ>/p-%p.profraw` を付けて、計装ビルドの ix68k を学習スクリプトで駆動する。終了時に `SIGTERM` を送る（6.3）。
3. まとめる: `xcrun llvm-profdata merge -output=<パッケージ名>.profdata <出力ディレクトリ>/*.profraw`
4. `packaging/release/pgo/` に置き、`README.md` に採取情報を書いてコミットする。

### 6.2 学習ワークロード

- 構成: disk 構成と x68060 構成のプロファイル設定（68060/50MHz、IC/DC は既定の ON）。
- 負荷: GCC.X BENCH（GHOSTED.C を 20 回コンパイル）を 1 回。
- 学習に使わなかった負荷（mint アイドル、NetBSD の 68060 起動）でも悪化せず、効果が出ることを確認済みのため、初版は BENCH だけにする。他の構成や負荷で悪化が見つかったときに、学習の範囲を広げる。

### 6.3 計装ビルドの終了

- 通常の終了経路では、プロファイルが書き出されない。ヘッドレスの自動学習では、`SIGTERM` で終了するのが扱いやすい。
- `X68K_PGO_GENERATE` が定義されたときだけ、`SIGTERM` のハンドラを `src/main.c` に入れる。ハンドラは `__llvm_profile_write_file()` を呼んでから `_exit(0)` する。非同期シグナル安全ではないが、学習専用のビルドに限る。

### 6.4 古さの判断と再生成

- プロファイルは、関数ごとの制御フローの形で、ソースと突き合わせる。形が変わった関数は無視され（`-Wprofile-instr-out-of-date`）、残りの関数には適用される。
- 古いプロファイルでも、削減は残る。変更前の mc68000 のソースに、変更後のコアで採ったプロファイルを適用して測ると（`execute_body` など 18 関数が不一致）、変更前コアの標準ビルドに対して BENCH のホスト CPU 秒が約 12% 減り、hard-overload はほぼ出なかった。新しいプロファイルでは約 17% 減る。
- 再生成の基準（コアの主要関数が変わったときだけ再生成する）:
  - `extern/cmc68000/src/cpu/` の関数のうち、`execute_body`・命令フェッチ高速経路・MMU・キャッシュ・ハンドラ群が変わったときは、リリース前に再生成する。判定は、前回のプロファイル採取時の mc68000 のコミット（`README.md` に記録）から現在の pin までの差分で行う。
  - それ以外の変更（周辺デバイス、描画、音声など）では、プロファイルを維持する。
  - どの場合も、リリース前に不一致の件数を確認し、`README.md` に記録する。維持する場合でも、不一致が採取直後の件数から大きく増えていれば再生成する。
- Apple clang の版が変わるとプロファイルの形式が読めなくなることがある。その場合はビルドがエラーになるので、再生成する。

## 8. 互換性・既知の制約

- 実機との差異: PGO はコンパイラの最適化だけで、エミュレーションの結果は変わらない。
- コンパイラ: Apple clang 21.0.0（Apple LLVM 21.0.0）で測定した。プロファイルの形式はコンパイラの版に依存する。
- プラットフォーム: 初版は macOS arm64 だけ。macOS x64 は、arm64 のプロファイルを共有できるかを未確認のため対象外にする。Linux（GCC）・Windows（MSVC）は別の仕組みで、未測定。Windows では LTCG が悪化した前例がある。
- 効果（macOS arm64、標準ビルドとの比較）:
  - GCC.X BENCH: ホスト CPU 秒が約 17% 減。標準では約 20〜32 フレーム/秒で出ていた hard-overload が、ほぼ出なくなる
  - mint アイドル: 約 22% 減
  - NetBSD 68060 の起動: 約 9% 減
  - NetBSD 68030 の起動: 揺らぎの範囲内（悪化は見られない）
  - `Release`（`-O3`）と `RelWithDebInfo`（`-O2 -g`）で、標準ビルドの差はなく、PGO の効果も同じ
- IR 計装（`-fprofile-generate`）との比較（2026-11-13、BENCH、標準・フロントエンド・IR を交互に 3 回ずつ）: 間接呼び出しの値プロファイルは採れ（`mc68k_execute` に畳み込まれた `execute_body` の飛び先は、上位 10 ハンドラで 81.6%、上位 20 で 99.8%）、ICP は効く。しかしホスト CPU 秒は、標準 32.2〜32.6、フロントエンド 26.9〜27.4（平均 27.11）、IR 27.0〜27.6（平均 27.23）で、IR とフロントエンドの差は揺らぎの範囲内。hard-overload も同等（フロントエンド 3〜7、IR 2〜4 フレーム、標準 653〜753）。学習外の負荷でも同じ傾向で、差は小さい。mint アイドル（60 秒窓の CPU 秒、3 回平均）は標準 41.23、フロントエンド 32.51、IR 31.85（IR が約 2% 小さく、3 回とも同じ向きだが、差は小さい）。NetBSD 10.1 68060/50MHz（fccache 版 HDS、`login:` 到達までの総 CPU 秒、3 回平均）は標準 75.43、フロントエンド 66.04、IR 66.12 で、差は揺らぎ内（hard-overload は標準 939〜1191、フロントエンド 141〜247、IR 123〜240 フレーム）。採用基準を満たさないため、フロントエンド計装を維持する。
- 学習と別の負荷（ゲームなど）、68000 構成での効果は未確認。学習に使った負荷に最適化が偏る可能性がある。
- PGO のビルドは、標準ビルドよりコンパイラの最適化の挙動が変わる。バグが顕在化するおそれがあるため、9 章の検証を必須にする。

## 9. テストと受入条件

| 観点 | テスト | 期待結果 |
| --- | --- | --- |
| オプションの検証 | `X68K_PGO_GENERATE` と `X68K_PGO_PROFILE` の同時指定、Clang 以外での指定、存在しないプロファイルの指定で configure する | いずれも `FATAL_ERROR` |
| 計装ビルドの出力 | 計装ビルドを起動して `SIGTERM` を送る | `.profraw` が書き出される |
| 通常ビルドへの影響 | オプションなしでビルドして全テストを実行する | 従来と同じ。`X68K_PGO_GENERATE` のコードが入らない |
| 適用ビルドのテスト | `stage.sh` が実行する `ctest` | 全件成功 |
| BENCH の出力 | 適用ビルドで IC/DC 既定の GCC.X BENCH を実行する | `GHOSTED.X` が 27358 バイト（標準ビルドと同じ） |
| 起動の回帰 | 適用ビルドで NetBSD（68060/50MHz、ソースビルド版）を起動する | ログインプロンプトに到達する |
| 速度 | 標準ビルドと適用ビルドを、プロセスを起動し直して交互に 3 回ずつ測る | BENCH のホスト CPU 秒と hard-overload を記録する。標準より減る |
| 不一致の件数 | `stage.sh` が表示する `ix68k` ターゲットの `profile-instr-out-of-date` | 件数を `README.md` に記録する |
