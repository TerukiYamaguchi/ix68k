# CPU 設計

## 1. 対象範囲

ix68k の CPU は mc68000 コアを使用します。本書は CPU 周辺の ix68k 固有の時間・メモリ接続方針を定めます。

## 2. MC68030 キャッシュ時間近似

MC68030 構成では、I-cache／D-cache の有効状態に応じて RAM/ROM アクセスの有効ペナルティを
バスフックで返します。コアはアクセス情報を渡すだけとし、キャッシュ可能性と待ち時間の判断は ix68k 側が持ちます。

- 現在はライン・タグ・充填を持たない最初の段階の時間近似を実装しています。
- MMIO/VRAM の待ち時間、自己書換えによる無効化、CACR の CI/CD/FI/FD、CAAR は対象外とします。
- 実装時は CACR と X68030 関連 MMIO のレジスタ互換性、RAM/ROM のアクセス分類、同期時刻、
  命令／データ別のテストを同時に整備します。

### 2.1 有効ペナルティの意味づけ

サイクルは3層に分かれます。L1（命令実行
クロック、命令ハンドラの返却値）は世代別であり、68030/68EC030 は `[UM30 §11.6]` の
I-Cache Case が仮定する「1バスアクセス 2 クロック」を前提にしています。`wait_penalty()`
（`src/bus/x68k_bus.c`）が返す L2 は、この前提（2クロック）を超える分を課金する設計だが、
後述のとおり現在の定数構成ではこの「超過分」を過不足なく計上できていません。

**UM30 自身が、バス応答には同期 (STERM) と非同期 (DSACKx) の2種があり最短クロック数が
異なることを明記している**（`[UM30 §1.1]` 印字 p.1-3「Enhanced Bus Controller Supports
Asynchronous Bus Cycles (three clocks minimum), Synchronous Bus Cycles (two clocks
minimum)...」、`[UM30 §7.2.8]` 印字 p.7-27「Although the processor can transfer data in a
minimum of three clock cycles when the cycle is terminated with DSACKx...」）。I-Cache Case
表が仮定する「2クロック」は同期 (STERM) の最短値であり、非同期 (DSACKx) の最短値はそれより
1クロック多い3です。

**ROM については、実機が非同期 (DSACKx) 応答であることを *X68030 Inside/Out*
（桒野雅彦、1994）p.130-131 の実測が裏付けます。** システムポート#5（`$E8E009`）の ROM
ウェイト設定 `$0` でもアクセスサイクル時間は本文で「200nS（5クロックサイクル）」と直接
述べられており、続けて「CPU の非同期バスサイクルは3サイクルですから2ウェイト入っている
ことになります」と明記する（設定値1つごとの延長幅も本文で「40nS（1クロックサイクル）」と
直接述べられている）。**DRAM についてこの資料が確認しているのは「設定値とウェイト数の
関係は DRAM のときと同様」という線形の延長幅（1あたり40nS）だけであり、DRAM の基準
クロック数・同期か非同期かは未確認**（該当する実測ページは OCR 未変換）。
Data Crystal「X68k/IOMAP」wiki の System Port #5 の項が定める「設定値+2のウェイト」という仕様値も、DRAM `$0` だけはスタティック
カラム動作の例外（0ウェイト、ページ跨ぎ4ウェイト）としており、ROM の「+2」則とは別枠です。

**理由1（「命令ハンドラは全モデルで MC68000 公称値を返すため基準が違う」）は L1 の世代別化で
当初の形では消えるが、実装を見ると別の穴が残っている（較正値に吸収されてはいない）。**
現行の較正定数は初期値のまま変わっていない（`X68K_WAIT_SCALE_NUM/DEN = 1/1`、
`X68K_RAM_WAIT_STATIC_COLUMN = 0`、`src/bus/bus_internal.h`）。既定構成 `$E8E009=$00` で ROM
を例にとると、モデル上は L1(2) + L2(`wait_penalty(0+2)=2`) = 4クロックだが、実機は非同期
3クロック + 2ウェイト = 5クロックである（上記実測）。1クロック/アクセスの差はどの定数にも
吸収されておらず、ix68k が実機より速く動く既知の過小評価として残っています。CACHE 無効時の
基礎コスト（後述）と同種の「どの層も担当していない」穴であり、現状の L2 の較正では埋まりません。

理由2（常時ヒット近似では、キャッシュヒット時に L1 へ含まれる基本バス時間を差し引けず、
差し引けるのは上乗せしたペナルティだけ）と理由3（実機はパイプラインで命令実行とバス
アクセスを重ねるため、生のウェイト数がそのまま実行時間の増分にならない）は、L1 の世代とは
独立に成立するため、L1 世代別化後も**変わらず有効**です。

**CACHE 無効時の基礎コスト（UM30 の No-Cache 列）はどの層も担当しない**。
L1 は CACHE 有効時の I-Cache Case 値に限定され、L2 は「ホスト側の追加ウェイトが 0 の領域では
課金しない」ため、CACHE off 時に wait を課金してもそれは「超過分の加算」であり基礎バス時間の
補填ではありません。上記の同期/非同期1クロック差も、この「どの層も担当しない」既知の過小評価の
一種として扱います。

### 2.2 較正規律

`wait_penalty()` の較正定数（`X68K_WAIT_SCALE_NUM/DEN`・`X68K_WAIT_MAX`・
`X68K_RAM_WAIT_STATIC_COLUMN`、いずれも `src/bus/bus_internal.h`）について、68030 キャッシュ
時間近似の当初設計は、ウェイト設定 `$00` の場合に限り「参照実装比が1.05を超えたら
`X68K_RAM_WAIT_STATIC_COLUMN` だけを動かす」という規律を定めてきました。本書はこれを
ウェイト設定全般へ広げ、次を定める：実測との乖離が確認された箇所に対応する定数を**1つだけ**
動かします。複数の定数を同時に動かすと、どの定数がどの誤差を吸収したのか切り分けられなくなる
ため行いません。動かす場合は根拠（対象ベンチの比、参照実装の種別）を添えて別課題として
起票し、測定結果を記録します。

### 2.3 合格基準の見直し結果

当初設計の判定幅を、L1 世代別化を前提に
見直しました。数値判定（±20%）は
交絡要因のない B1（256 バイト未満の RAM 常駐タイトループ）のみに絞り、B3（ROM-fetch proxy）・B4（D-cache
read。原因調査の結果、参照実装との比較で cache-on 時の L1 ベース値差に起因する比率指標の
アーティファクトと判明、コード欠陥なし）・B5（write-through と参照実装の write-wait 免除の
差）は B2（512 バイトを超える RAM 常駐の実行範囲）と同じ「既知差・記録のみ」に格下げしました。ウェイト設定 `$00` の較正判断（§2.2 の
規律）は、参照実装比が B1・B4 とも 1.04（閾値 1.05 以下）のため較正不要と判断し、
`X68K_RAM_WAIT_STATIC_COLUMN` は初期値のまま維持します。較正定数は今回いずれも変更していません。
