# CRTC 実装状況

`src/bus/x68k_bus.c` に実装されている CRTC のレジスタ単位のサポート状況一覧。
**アドレスマップ全体は `docs/ix68k-internals/addrmap.md` を参照。
FDC は `docs/ix68k-internals/support/fdc_support.md`、MFP は `docs/ix68k-internals/support/mfp_support.md`、
スプライトコントローラは `docs/ix68k-internals/support/sprite_support.md`、IOCS は
`docs/ix68k-internals/support/iocs_support.md`、ビデオコントローラは
`docs/ix68k-internals/support/video_controller_support.md` を参照。**

> **必須**: CRTC のレジスタ・機能を実装・変更したら、このファイルの該当表を必ず更新します。

| R18 | $E80024 | グラフィック画面スクロール X3 | ✅ 16色4ページの page3 |
| R19 | $E80026 | グラフィック画面スクロール Y3 | ✅ 同上 |
| R20 | $E80028 | メモリモード/表示モード制御 | ✅ 表示解像度(HD/VD)判定に使用。色モード/ページ数はうちの実装では使わず `$93C` ベースでルックアップ（`x68k_bus_get_gvram_color_mode`/`x68k_bus_is_gvram_1024dot`）だが、**R20自体は色数/ページ数を正しく区別できる**（2026-07-08訂正）。`_CRTMOD` 単体はR20の色数ビットを仮値（port=3固定）のまま残す設計で、続けて `_G_CLR_ON`($90) を呼ぶと `$93C` から計算した正しいSIZ/COLがR20・ビデオコントローラR0に反映される（ROM `$FFAE32`、動作検証済み: mode0→R20上位0x04、mode4→0x00、mode8→0x01、mode12→0x03、いずれも図54のビット定義と一致）。グラフィックIOCSを使うソフトは必ず`_G_CLR_ON`を呼ぶため、実運用上はR20だけでも判別可能。うちの`$93C`直接参照はROMの計算と結果的に同じ答えを返すため実装変更は不要。**表示解像度判定のバグ修正**（2026-07-08、`_CRTMOD`全代表モード動作検証で発見）: `x68k_bus_get_display_size()`がHD/VDの2ビットだけで「R20未初期化→512×512」を判定していたため、HD=00/VD=00という正当な値（256×256表示、mode2/6/10/14等）まで誤って512×512にフォールバックしてきました。R20ワード全体（上位・下位バイトとも0）で未初期化判定するよう修正 |
| R21 | $E8002A | 同時アクセス(SA)／ラスタコピー／高速クリアプレーン選択 | 🔄 SA(bit0=crtc_regs[0x2A])+AP(bit7-4=crtc_regs[0x2B]上位)実装。bit9(crtc_regs[0x2A]bit1)でR23アクセスマスクの適用有無をゲート、bits3-0(crtc_regs[0x2B]下位、CP)で**ラスタコピー対象プレーンとグラフィック高速クリア対象プレーンの両方**を選択（XEiJ CRTC.java準拠、2026-07-06実装）。ただし1024ドットモードの高速クリアはCPを無視しGVRAM 2MB全域が対象になる（XEiJ `crtRapidClear` の `crtMemoryModeCurr >= 4` 分岐と同じ） |
| R22 | $E8002C | ラスタコピー動作用（転送元/転送先ラスタ） | ✅ アクションポート bit3 が1の間、書き込み時の即時コピーに加えて毎水平フロントポーチでも参照される |
| R23 | $E8002E | テキスト画面アクセスマスクパタン | ✅ `_TXYLINE`/`_TXLINE` 用に実装。R21 bit9 でゲート |
| CRTC動作ポート | $E80480 | bit0=画像取り込み・bit1=高速クリア・bit3=ラスタコピー制御 | 🔄 bit1（グラフィック画面高速クリア）・bit3（ラスタコピー）を実装、bit0（画像取り込み、オプションのカラーイメージユニット必須）は未実装。実体は**奇数バイト $E80481**（$E80480側は上位バイト扱いで意味を持たない）。**bit1**: 書き込みの瞬間に対象行をすべて同期的にクリアする（`x68k_bus_crtc_rapid_clear()`、XEiJ `CRTC.crtRapidClear()` 準拠）。実機は次のV-DISP立ち上がりから1フレーム（インターレース時2フレーム）かけて表示ラスタ1本ずつ消すが、ix68kは非同期タイミングモデルを持たないためクリア自体は書き込み時の同期実行に簡略化しています。ただし完了フラグ(bit1)の読み戻しはトリガ書き込み直後には落とさず、**次にこのポートが読まれた瞬間だけ1（実行中）を返し、2回目以降の読み出しから0（完了）に戻す**（`crtc.rapid_clear_pending`、`src/bus/x68k_bus.c` read8()のCRTC分岐）。これは「トリガ後まずbit1が1になったことを確認してから0を待つ」という2段階ポーリングを行うソフト（電脳倶楽部Vol.37のブートローダ等）が、書き込み直後に即0を返すと1を一度も観測できず別の無限ループに陥るため。クリア範囲は**縦=表示高さ分のみ**（R20 VDから算出。実画面全体ではない、インサイドX68000 図28）で、ページごとのYスクロール(R13/R15/R17/R19、プレーン番号と同順)を加えて実画面内で球面的に巻き戻します。**横=実画面の幅いっぱい**（512ドットモード=1024バイト/行、1024ドットモード=2048バイト/行）。**既知の差異**: 実機は表示画面が実画面より狭いとき横方向の画面外が消え残る（同 図28）が、XEiJ同様この簡略化は行っていません。**bit3**: MPUがラスタコピー機能をON/OFFする**保持型（レベル）スイッチ**（XEiJ CRTC.java crtRasterCopyOn/crtDoRasterCopy、L233-235コメントが「0→1のトリガーでもCRTCの動作終了フラグでもない」と明記）。書き込み時に即時コピーを1回行う（MPX68K commit f59c07dが残した互換経路と同じ、`x68k_bus_crtc_raster_copy()`）のに加え、bit3が1の間は各ラスタの水平フロントポーチ相当の時点（`crtc_raster_emit_line()`、`x68k_bus_crtc_raster_advance()`/`x68k_bus_crtc_raster_flush()`経由でライン到達ごとに呼ばれる）でも同じコピーを繰り返す（2026-09-02実装）。0を書くまで保持されるため`x68k_bus_read8(0xE80481)`のbit3読み戻しは自動クリアされない（rapid_clearのbit1とは対照的）。R22を一度だけ設定してコピー元だけを更新し続けるソフト（MPX68K `tools/raster-copy-test/`で目視検証済み）で正しく画面が追従するようになった |

## システムポート（$E8E000-$E8E00F、CRTCとは別チップ）

『Inside X68000』記載の6レジスタと、実装状況の監査
（2026-07-29）。物理的にはCRTCではないが、アドレス空間は`CRTC_BASE`
(`$E80000`)〜`+CRTC_SIZE`(`0x10000`)の汎用passthrough配列(`crtc_regs[]`)に含まれて
おり、専用のread/writeハンドラは無い。

| # | アドレス | 内容 | 実装状況 |
|---|---|---|---|
| 1 | $E8E001 | CONTRAST（画面コントラスト、下位4bit） | ビデオコントローラの機能。`video_controller_support.md` を参照 |
| 2 | $E8E003 | TV CTRL / 3D-L / 3D-R（ディスプレイ/3Dスコープ制御） | ❌ 同上 |
| 3 | $E8E005 | カラーイメージユニット制御（IMAGE IN出力） | ❌ 同上（オプション機器のため実害はほぼ無いと推測） |
| 4 | $E8E007 | bit3=KEY CTRL / bit2=NMI RESET / bit1=HRL / bit0,4-7=未使用 | ⚠️ **bit1(HRL)のみ**`x68k_bus_get_dot_width_units()`が読み取り、表示1ドットの横幅（＝ホストのウィンドウ幅）算出に使用。bit2(NMI RESET)・bit3(KEY CTRL)は保持のみで意味を持たない |
| 5 | $E8E00D | SRAM Write Enable Control（$31書き込みで許可、他の値で禁止） | ❌ 未実装。**保護は一切効いておらず、SRAMは常に書き込み可能**（値の大小に関わらず素通し） |
| 6 | $E8E00F | Power OFF Control（$00→$0F→$0Fの順で本体電源OFF） | ✅ 実装済み。前面スイッチOFF（`gpip2_level==1`）の間だけ各バイト書込みで `$00,$0F,$0F` を検出し、`x68k_bus_power_off_requested()` のラッチを立てて main ループが通常の終了経路へ進みます。ON中の書込みはステートを待機へ戻します。ワード/ロング書込みも `write8` 経由で数えます。途中ステートはリセットでクリア、要求は残る。実機でスイッチON時に書いた場合・ユーザーモード書込みのバスエラー時の挙動は未検証 |

## 複数ページ・バンク切り替え

GVRAM ページ表示（`x68k_bus_get_gvram_pages` によるページ別ベースオフセット
+ R12-R19 スクロール）は ✅ 実装済み（2026-07-07）。**このセクションは
2026-07-08 まで「❌ 未実装」のまま古い記述が残っていた**（他セクションの更新と
不整合だったため訂正）。

ビデオコントローラ R1 の GP0-3（ページ間表示優先順位、$E82500 下位8ビット）は
✅ `gvram_apply_priority()`（`x68k_bus_get_gvram_pages` 内）で解釈し、ページ合成順に
反映する（2026-07-08実装）。**2026-07-08 動作検証で確認**: 4ページ
モード(mode4/6)・2ページモード(mode8/10)いずれも、同一座標に複数ページで異なる
色を描画した状態でR1のGP0-3を書き換えると（4ページ: $E4→$E1、2ページ: $E4→$4E、
いずれも page1 を最前面にする設定）、表示が page0 の色→page1 の色に正しく切り替わる
ことを確認した（実装前は変化しなかった）。

## 検証メモ（2026-07-08、_CRTMOD 代表11モード動作検証）

`_CRTMOD`(mode0,2,4,6,8,10,12,14,16,17,18) それぞれで
「_CRTMOD+_G_CLR_ON二段初期化 → 各ページに色分け四角を描画 → スクロール →
（複数ページのみ）優先順位切替」を実施（テストコード:
`tools-x68k/asmtest/crtmod_test.s`）。

- **描画**: 全11モードで各ページのGVRAM書き込みが期待アドレスに正しく反映される
  ことを確認（1024dotモードのページベース、512dotモードの4ページ/2ページの
  ベースオフセットとも一致）。
- **スクロール**: R12(page0 X)書き換えが該当ページのみに反映されることを確認。
  実画面512dotモード（mode12/14）では 球面スクロール（mod 512 wraparound）も
  正しく機能することを確認。
- **優先順位**: 検証時点では未実装だったが、動作検証結果を受けて
  `gvram_apply_priority()` を実装。再検証で4モードとも正しく切り替わることを確認。
- **副産物のバグ発見**: `x68k_bus_get_display_size()` がHD/VDの2ビットだけで
  「R20未初期化→512×512固定」と誤判定しており、正当なHD=00/VD=00（256×256表示、
  mode2/6/10/14等）まで512×512にフォールバックしてきました。R20ワード全体が0の
  ときだけ未初期化とみなすよう修正済み（同日）。
- **副産物の観察（バグではない）**: `_G_CLR_ON`はROM委譲だが、GVRAMクリアは
  page0のみが対象で、page1-3は前のモードの描画内容が残ったままになる
  （実機/ROMの実際の挙動と推測、うちは単にROMを素通しで実行しているだけ）。
  複数ページモードを跨いでテストする際は要注意。
- **解決済み（幅768止まり）**: mode17/18（実画面1024、表示1024×424/1024×848）の
  幅がHDテーブル(旧`hdtab[]`、768までしか値を持たない)の都合で768止まりになる
  問題は2026-07-28の正方形ドットモード対応で幅の算出を
  HDビットからR02/R03差分ベースに置き換えた際に副次的に解消済み。
  2026-08-22のホストウィンドウサイズ実測（CRTMOD 17で1024px確認）でも
  再確認されています。当時の調査ではこの副次修正に気づかず「未検証」のまま残って
  いた（2026-09-02訂正）。
- **高速クリアのタイミング簡略化**: CRTC動作ポート bit1 のクリア自体は書き込み時に
  同期完了するため、実機の「1フレームかけて上から順に消える」途中経過をラスタ割り込み
  で観測する演出は再現できません。完了フラグの読み戻しだけは「次の1回の読み出しで1、
  それ以降0」という最小限の状態を持たせてあり（`crtc.rapid_clear_pending`）、
  トリガ後に1→0の2段階を確認するポーリングを行うソフトにも対応しています。bit3の
  ラスタコピーは2026-09-02にbit1と異なる「保持型・毎フロントポーチ再実行」方式へ
  変更済み（上表参照）。
