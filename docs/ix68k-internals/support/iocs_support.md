# X68000 IOCS サポート状況表

更新: 2026-09-03

出典: Data Crystal [X68k/IOCS](https://datacrystal.tcrf.net/wiki/X68k/IOCS)（関数名・説明）。状態は `src/iocs.c` の
IOCS ハンドラ実装に基づきます。Data Crystal が定義する全 IOCS コール（$00–$FF、欠番除く）を網羅。

## 凡例

| 記号 | 意味 |
|------|------|
| ✅ | 実装済み（独自ハンドラで正常な値を返す） |
| 🔄 | ROM に委譲（`return 0` → ベクタテーブル経由で ROM/ドライバが処理） |
| 🔧 | スタブ（未接続デバイス等に固定値を返す） |
| ❌ | 自前ハンドラ未実装（`default` 経由で ROM 委譲。`IOCS unimplemented` ログを出す点だけが 🔄 と異なる） |
| ⬚ | 欠番（Data Crystal に定義なし。呼ばれると `default`＝❌ と同じく ROM 委譲） |

**ROM委譲監査列**: 「本来は実ROMハンドラに委譲すべきところ、固定値・不完全な自前実装のまま
放置されている」疑いを示します。`_BOOTINF`が`$90`固定でSCSI-HD起動完了を長時間ブロックして
いた実例を踏まえ、同種のパターン（デバイス種別によって固定値を出し分けている
✅/🔧行）を洗い出す目的の列。**空欄はまだ個別監査していないことを意味し、「問題なし」の
確認ではない**。新機能追加時にこの列が空の関連行を見つけたら、着手前に監査すること。

| 記号 | 意味 |
|------|------|
| ✅済 | このセッションでROM委譲または正しい実装に修正済み |
| 🔍要確認 | 同様のパターン（デバイス種別で固定値を出し分け）が残っており未検証 |

> **委譲の原則**: `PC >= 0xF80000`（ROM 内コード）からの `TRAP #15` は常に ROM ハンドラへ委譲します。
> 下表の状態は **アプリ（PC<0xF80000）から呼ばれた場合**の挙動。
> Data Crystal に載らない関数番号（$9d–$9f, $a6–$ab, $d0–$d2, $d9–$de, $e0–$ef, $f4, $f6–$fc）は
> 欠番で、呼ばれると `default`（❌）になります。
>
> **`default` は D0=0 で握りつぶさず ROM へ委譲します。** IOCS ベクタテーブル（`$0400 + fn*4`）は
> IPLROM が全256エントリ分を初期化しており、「(未公開)」とされる番号にも実ハンドラがあります。
> 握りつぶすと呼び出し元は「設定できた」と誤認したまま進むため、症状が出る場所と原因が
> 大きく離れた不具合になる（$91/$93 を握りつぶして mint.x の PIC ビューアが
> 512x512・65536色へ切り替わらなかった実例。`IOCS unimplemented` ログで検知できる）。

常駐ドライバがIOCS `_FNTADR`($16)経由でANKフォントを実行時に差し替えると、
`read_bitmap_text`/`run_command`が前提とするROM固定オフセットのCGROM参照と
食い違います。ゲスト側で`tools-x68k/fntadr/`（`make`でビルド）を実行し
`_B_PRINT`経由で実アドレスを`FNTADR=XXXXXXXX;`として報告させると、0x21の
ROM委譲ハンドラがこのマーカーを検出して以後の照合基準を切り替えます。報告は
リセットで失われます。
